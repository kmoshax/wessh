# Rust media stack for a real-time face-swap desktop app: capture, video I/O, GUI and live preview, virtual camera (Linux/Windows/macOS, as of Sept 2026)

## Webcam capture: which crate or approach (nokhwa, v4l, eye, gstreamer-rs, FFmpeg bindings), and what pixel format and decode costs to expect?

### Takeaway
nokhwa is still the default cross-platform capture crate. It is maintained, v0.10.11 shipped in May 2026, and it has V4L2, MSMF and AVFoundation backends, MJPEG decode, and an optional wgpu texture output. Use the `v4l` crate directly on Linux when you need control over mmap/userptr zero-copy buffers. Use gstreamer-rs when you want hardware decode and one pipeline abstraction on every OS, at the cost of shipping GStreamer as a heavy runtime dependency.

### Cited Findings
- nokhwa's latest release is 0.10.11 (May 15, 2026). It gets about 68.8K downloads a month, is about 9K SLoC, has 27 contributors, is maintained by l1npengtul, and 50 crates depend on it. — [lib.rs nokhwa](https://lib.rs/crates/nokhwa)
- nokhwa backends: Video4Linux (Linux), MSMF (Windows) and AVFoundation (macOS) all support input, query and device query. OpenCV is input-only and the README says it "may be bugged". WASM is also supported. GStreamer is not listed as a current backend. — [GitHub l1npengtul/nokhwa](https://github.com/l1npengtul/nokhwa); [lib.rs](https://lib.rs/crates/nokhwa)
- nokhwa features include an `output-wgpu` wgpu texture output, threaded camera access, and MJPEG decoding through mozjpeg. — [lib.rs nokhwa](https://lib.rs/crates/nokhwa); [docs.rs nokhwa](https://docs.rs/nokhwa/latest/nokhwa/)
- nokhwa repo status: about 813 stars, 202 forks, 57 open issues and 10 open PRs, on the `senpai` branch. Nothing says it is unmaintained. — [GitHub](https://github.com/l1npengtul/nokhwa)
- The license is reported inconsistently. The GitHub README says Apache-2.0 or MIT; lib.rs lists Apache-2.0. — [GitHub](https://github.com/l1npengtul/nokhwa) vs [lib.rs](https://lib.rs/crates/nokhwa)
- There is an actively published fork, `videocall-nokhwa` (0.10.9), maintained for the videocall.rs ecosystem. — [docs.rs videocall-nokhwa](https://docs.rs/crate/videocall-nokhwa/latest)
- `v4l` (libv4l-rs): v0.14.0 is from May 12, 2023, so there has been no release in more than three years. It is still widely used (about 387K downloads a month, 49 dependent crates) and MIT-licensed. It supports mmap and userptr streaming, FourCC format configuration and zero-copy. It has two backends: `libv4l`, which adds userspace format conversion such as RGB3 emulation but no userptr, and raw `v4l2`, which has full features but leaves conversion to you. — [lib.rs v4l](https://lib.rs/crates/v4l); [GitHub raymanfx/libv4l-rs](https://github.com/raymanfx/libv4l-rs)
- gstreamer-rs gets about 564K downloads a month. It uses a pipeline model with appsink/appsrc and is not FFmpeg-based. — [dev.to "State of media processing in Rust (2026)"](https://dev.to/yeauty/the-state-of-media-processing-in-rust-2026-what-each-crate-actually-covers-2k2c)
- Slint ships a GStreamer example that produces OpenGL textures and imports them into `slint::Image`. This shows gstreamer-rs can reach a GPU texture without a CPU copy. — [Slint examples README](https://github.com/slint-ui/slint/blob/master/examples/README.md); [Slint discussion #5463](https://github.com/slint-ui/slint/discussions/5463)

### Inferences
- Recommended default: nokhwa with `input-native`. Request MJPEG at 1080p/720p 30–60 FPS (USB 2.0 cameras usually give YUYV only at low frame rates). Decode MJPEG yourself with turbojpeg/mozjpeg on a worker thread, or ask for NV12/YUYV and convert to RGB on the GPU with a wgpu compute shader. That way the CPU never touches per-pixel color conversion, which the face-swap model needs (RGB/BGR float) anyway.
- On Linux, dropping to `v4l` gives mmap buffers and exact FourCC control. The crate has not had a release since 2023, so pin it and expect to vendor patches.
- Hardware MJPEG/H.264 decode through webcams mostly matters for high-resolution MJPEG. In practice gstreamer-rs (`vaapijpegdec`/`nvjpegdec`/`vtdec`) or FFmpeg hwaccel are the only Rust paths to it. nokhwa's MJPEG decode is CPU-only (mozjpeg).
- `eye`/`eye-rs` did not come up in current sources. Treat it as dormant or niche unless someone verifies otherwise.

### Gaps
- I found no benchmarks of MJPEG decode cost (ms/frame at 1080p) or of nokhwa against GStreamer capture latency.
- I did not verify the `eye` crate's status, the current gstreamer-rs version number, or hardware-accelerated webcam decode in Rust (NVJPEG/VAAPI JPEG).
- I did not check nokhwa's open issues for specific MSMF or AVFoundation bugs, such as format negotiation or permissions prompts on macOS.

## Batch video file processing: ffmpeg-next vs rsmpeg vs gstreamer-rs vs ffmpeg-sidecar, hardware encode, audio passthrough and licensing

### Takeaway
There are three workable paths. ffmpeg-sidecar runs a separate ffmpeg binary: simplest to build, best for licensing isolation, and audio passthrough is trivial with `-map 1:a -c:a copy`. rsmpeg is an in-process binding that tracks FFmpeg 6/7/8. ffmpeg-next is the most popular binding but is officially in maintenance-only mode. For portable redistribution, an LGPL build of FFmpeg that is dynamically linked or run as a separate executable, without `--enable-gpl` and `--enable-nonfree`, is the safe option.

### Cited Findings
- ffmpeg-next is "currently in maintenance mode". It supports FFmpeg 3.4 through 8.0, has about 7.4M all-time downloads, and is a fork of the abandoned `ffmpeg` crate. — [crates.io ffmpeg-next](https://crates.io/crates/ffmpeg-next); [lib.rs](https://lib.rs/crates/ffmpeg-next); [GitHub zmwangx/rust-ffmpeg](https://github.com/zmwangx/rust-ffmpeg)
- rsmpeg (larksuite/ByteDance org, about 877 stars) supports FFmpeg 6, 7 and 8, with 8.0 added in 0.18.0. It mirrors the C API, can link statically via rusty_ffmpeg, and is described as having a slow release cadence (about 11 months without major movement). — [dev.to 2026 survey](https://dev.to/yeauty/the-state-of-media-processing-in-rust-2026-what-each-crate-actually-covers-2k2c)
- ffmpeg-sidecar wraps a standalone FFmpeg binary in an iterator of raw frames, has no Cargo dependencies on the Rust side, and needs the ffmpeg executable at runtime. It gets about 131K downloads a month (about 1.9M all-time). — [dev.to survey](https://dev.to/yeauty/the-state-of-media-processing-in-rust-2026-what-each-crate-actually-covers-2k2c); [GitHub releases](https://github.com/nathanbabcock/ffmpeg-sidecar/releases)
- video-rs (about 32K downloads a month) is described as "still a work-in-progress" and has no audio API. Its successor, `rave`, is "not ready for use yet". — [dev.to survey](https://dev.to/yeauty/the-state-of-media-processing-in-rust-2026-what-each-crate-actually-covers-2k2c)
- ez-ffmpeg is an in-process FFmpeg runtime with CLI parity via `from_cli()` (v0.15+). The survey's author maintains ez-ffmpeg, so its comparisons may be biased. ac-ffmpeg has not released in 14 months. — [dev.to survey](https://dev.to/yeauty/the-state-of-media-processing-in-rust-2026-what-each-crate-actually-covers-2k2c)
- FFmpeg licensing: the default license is LGPL 2.1+. `--enable-gpl` or libraries such as x264/x265 make the build GPL, and `--enable-nonfree` (for example fdk-aac) makes it non-redistributable. The LGPL checklist is: dynamic linking, no GPL/nonfree flags, publish the source and the configure line, attribution in the About box, don't rename the libs, and update the EULA. The page also warns that MPEG patents can matter for commercial use. — [ffmpeg.org/legal.html](https://ffmpeg.org/legal.html)
- A Tauri maintainer's 2026 answer names `mp4`, `mp4-atom`, `ffmpeg-next` and `rsmpeg` for muxing, and `openh264`, `ffmpeg-next` and VideoToolbox for decode. — [tauri discussion #15171](https://github.com/orgs/tauri-apps/discussions/15171)

### Inferences
- Batch mode (swap faces in a video file): the lowest-risk design is ffmpeg-sidecar. Decode to `rawvideo` rgb24/bgr24 on stdout, run inference, then pipe frames into a second ffmpeg process with `-f rawvideo -i - -i original.mp4 -map 0:v -map 1:a? -c:a copy`, plus a hardware encoder such as `h264_nvenc`, `hevc_nvenc`, `h264_videotoolbox`, `h264_qsv` or `h264_vaapi`, falling back to `libopenh264`/`libx264`. Sidecar keeps FFmpeg outside your binary for LGPL/GPL purposes, since it is a separate program, and lets users swap in their own ffmpeg build.
- Encoder licensing: x264/x265 force GPL. NVENC, QSV, VAAPI, AMF and VideoToolbox are available in LGPL builds, and openh264 is BSD with Cisco's patent-covered binaries. So an LGPL build plus hardware encoders plus openh264 as a software fallback avoids GPL. (Based on general FFmpeg knowledge; the legal page confirms only the GPL/nonfree triggers.)
- In-process choice: prefer rsmpeg over ffmpeg-next for new code that must track FFmpeg 7/8. Use ffmpeg-next if you want the larger example base and can accept maintenance-only status. gstreamer-rs is the better fit if you also use GStreamer for capture and hardware decode.

### Gaps
- I found no Rust-specific benchmarks comparing in-process bindings with sidecar pipe overhead. At 1080p30 rgb24 the pipe carries about 187 MB/s, which is my own arithmetic and not a sourced number.
- I did not verify the current rsmpeg or ffmpeg-sidecar version numbers as of September 2026, or how mature gstreamer-rs's hardware encoder elements are.

## GUI: which native Rust GUIs handle a continuously updating video texture efficiently, and can inference output be rendered directly as a wgpu texture?

### Takeaway
egui/eframe (wgpu backend), Slint (wgpu 27/28 backend) and iced (0.14, wgpu 27, `shader` widget) can all show a GPU-resident wgpu texture every frame without a CPU readback. egui does it with `Renderer::register_native_texture` / `update_egui_texture_from_wgpu_texture`, Slint with `slint::Image::try_from(wgpu::Texture)`, and iced with a custom `shader::Program`. gpui is capable but pre-1.0 and has no stable external-texture API. egui is the lowest-risk choice for a tool-style app.

### Cited Findings
- egui-wgpu 0.36.2 `Renderer` has `register_native_texture(&Device, &TextureView, FilterMode) -> TextureId` (the texture must be `Rgba8Unorm`), `register_native_texture_with_sampler_options`, `update_egui_texture_from_wgpu_texture(..., id: TextureId)` and a sampler-options variant. These let the app reuse a TextureId while swapping the bound wgpu texture. — [docs.rs egui_wgpu::Renderer](https://docs.rs/egui-wgpu/latest/egui_wgpu/struct.Renderer.html)
- History: native wgpu texture registration was missing from the newer `egui-wgpu` (issue #1662, 2022), and updating via `update_texture` each frame was called "probably a performance hit". The CPU path recommended for frequent updates is `TextureHandle::set` rather than calling `load_texture` every frame. — [egui #1662](https://github.com/emilk/egui/issues/1662); [egui discussion #2994](https://github.com/emilk/egui/discussions/2994)
- An open egui issue (#7761, "WGPU backend transition: performance, issues and suggestions") covers wgpu-backend performance concerns. A separate panic occurs when unloading a texture in the same frame it is rendered (#5224). — [egui #7761](https://github.com/emilk/egui/issues/7761); [egui #5224](https://github.com/emilk/egui/issues/5224)
- Slint can import externally produced `wgpu::Texture`s via `slint::Image::try_from<wgpu::Texture>()`, or render an underlay/overlay via `Window::set_rendering_notifier()`. You select wgpu with `slint::BackendSelector::require_wgpu_28()`, which accepts a preconfigured device and required features. Slint ships a `wgpu_texture` example and a GStreamer player example. — [slint::wgpu_28 docs](https://docs.slint.dev/latest/docs/rust/slint/wgpu_28/); [Slint PR #8278](https://github.com/slint-ui/slint/pull/8278); [Slint examples](https://github.com/slint-ui/slint/blob/master/examples/README.md)
- There is a community FFmpeg-plus-Slint wgpu video player with threaded demux/decode/audio/UI stages and bounded queues. — [singh-ps/rs-wgpu-video-player](https://github.com/singh-ps/rs-wgpu-video-player)
- Slint pitfall: using a rendering notifier with the FemtoVG backend recreates render pipelines every frame (issue #12030). — [slint #12030](https://github.com/slint-ui/slint/issues/12030)
- iced 0.14.0 (released December 7) added reactive rendering, time-travel debugging, an animation API, "concurrent image decoding and uploading", and moved to wgpu 27.0. The `shader` widget has existed since 0.12 and renders custom wgpu primitives inside iced. — [iced 0.14.0 release](https://github.com/iced-rs/iced/releases/tag/0.14.0); [iced 0.12.0 release](https://github.com/iced-rs/iced/releases/tag/0.12.0); [iced shader docs](https://docs.iced.rs/iced/widget/shader/index.html)
- gpui (Zed) is "still in active development and pre-1.0" with frequent breaking changes. Standalone use relies on unofficial mirrors (`gpui-standalone` with date tags such as 2026-08-21, and the `gpui-unofficial` crate). An external-texture primitive that composites without readback is only a proposal. — [gpui README](https://github.com/zed-industries/zed/blob/main/crates/gpui/README.md); [realab/gpui-standalone](https://github.com/realab/gpui-standalone); [lib.rs gpui-unofficial](https://lib.rs/crates/gpui-unofficial)

### Inferences
- Zero-copy design: create one `wgpu::Device` and share it between the inference postprocess and the GUI. eframe exposes its wgpu `RenderState`, and Slint's `require_wgpu_28` accepts your device. Write the swapped frame into an `Rgba8Unorm` texture with a compute shader, and have the GUI sample it. If ONNX Runtime/TensorRT outputs into CUDA memory, there is no portable zero-copy route into wgpu. You would need a CUDA→D3D12/Vulkan interop hack, so plan on one `queue.write_texture` upload per frame. A 1080p RGBA upload is about 8 MB and costs roughly 1 ms on a PCIe GPU (my estimate, not sourced), which is fine at 60 FPS.
- Ranking for this app: egui/eframe for fastest development and a proven native-texture API. Slint if you want a designer-friendly declarative UI with a first-class wgpu texture import. iced if you prefer Elm architecture, where the `shader` widget needs more boilerplate. gpui, Makepad, Xilem and Dioxus native/Blitz are too immature or unstable for a shipping product today.

### Gaps
- Makepad, Xilem/Masonry and Dioxus native/Blitz video-texture support was not researched. I found no sources on their external-texture APIs.
- I found no published FPS/latency benchmarks comparing egui, Slint and iced for per-frame texture updates.

## Tauri 2 live video preview: transport options, measured numbers, webview differences, native wgpu overlay, and the verdict against native Rust GUIs

### Takeaway
Tauri 2 can reach 30 FPS at moderate resolutions by pushing raw or JPEG bytes over `ipc::Channel`, `ipc::Response` or a custom protocol into a `<canvas>`. Every frame still crosses a message-passing bridge that the Tauri team chose deliberately over shared memory, and Linux WebKitGTK often falls into software compositing. The native-wgpu-under-webview approach is fragile. **Verdict: for a 30–60 FPS face-swap preview, use a native Rust GUI such as egui or Slint on wgpu. Tauri is acceptable only as a settings/control shell, not for the video surface.**

### Cited Findings
- Tauri maintainer (May 2022): "Tauri chose _Message Passing_ as it's IPC architecture not _Shared Memory_… trade performance in exchange for security." — [tauri discussion #4177](https://github.com/tauri-apps/tauri/discussions/4177)
- In November 2025 a RustDesk commenter in the same thread said they chose Flutter over Tauri years earlier because of this frame-buffer limitation. — [tauri discussion #4177](https://github.com/tauri-apps/tauri/discussions/4177)
- Tauri 2 rewrote IPC to support raw (non-JSON) payloads and added the Channel API for streaming large data. — [Tauri 2.0 release](https://v2.tauri.app/blog/tauri-20/); [Tauri 2.0 beta](https://v2.tauri.app/blog/tauri-2-0-0-beta/)
- Tauri maintainer guidance (April 2026) lists three options:
  - Remux H.264 into fragmented MP4 and feed `<video>` via MSE (hardware decode in the webview). This is recommended for compressed streams.
  - Decode in Rust, convert YUV→RGBA, and send JPEG or raw bytes to a canvas. This is described as "CPU-heavy at 1080p30" because of serialization over the bridge; use `tauri::ipc::Response` with bytes or a custom protocol to avoid JSON.
  - A native overlay: a separate native surface (for example gstreamer-rs playbin) with a transparent webview on top, needed for latency budgets under about 150 ms.
  — [tauri discussion #15171](https://github.com/orgs/tauri-apps/discussions/15171)
- Measured (third-party tauri-conduit, macOS aarch64): a 64 KB blob round trip took 6.7 ms through Tauri invoke/JSON versus about 600 µs with a binary protocol. WebView bridge overhead is about 300 µs per call. The Rust-side-only numbers exclude the WebView bridge and JS parse. No data was published for payloads of 1 MB or more. — [tauri-conduit BENCHMARKS.md](https://github.com/userFRM/tauri-conduit/blob/master/BENCHMARKS.md)
- tauri-wire (third party) reports that JSON.parse on a 5 KB payload costs 0.5–2 ms, while DataView reads are near-instant. This argues for binary framing over Channel/Response. — [userFRM/tauri-wire](https://github.com/userFRM/tauri-wire)
- macOS: Tauri/WKWebView is capped at 60 FPS by default. A third-party plugin disables the cap. — [tauri-plugin-macos-fps](https://github.com/userFRM/tauri-plugin-macos-fps)
- Linux WebKitGTK: canvas and WebGL can "silently land on a slow path". With `WEBKIT_DISABLE_DMABUF_RENDERER=1`, a common workaround for NVIDIA and Wayland glitches, WebKitGTK disables accelerated compositing and paints in software, copying each canvas redraw back to the CPU. Long-standing Tauri issues report slow canvas rendering and generally poor performance on Linux. — [NegativeConverter #263](https://github.com/lexluthor0304/NegativeConverter/issues/263); [tauri #5761 "Canvas HTML slow render on Linux"](https://github.com/tauri-apps/tauri/issues/5761); [tauri #3988 "Bad performance on linux"](https://github.com/tauri-apps/tauri/issues/3988); [Tauri Linux graphics docs](https://v2.tauri.app/develop/debug/linux-graphics/); [WebKitGTK-Test tool](https://github.com/Studio-200A/WebKitGTK-Test)
- WebKitGTK lacks WebRTC. CrabNebula ships `tauri-plugin-webrtc` with a pure-Rust engine that uses WebCodecs in the webview to encode and decode VP8 and draws decoded frames to a canvas. — [crabnebula-dev/tauri-plugin-webrtc](https://github.com/crabnebula-dev/tauri-plugin-webrtc)
- Native wgpu plus webview: wry has a `wgpu.rs` example that sets `transparent = true` and, on Windows, `with_clip_children(false)`. Known bugs: the webview does not blend over wgpu content on Windows 11 (wry #1212, #1331), and after wgpu 24 the webview rendered behind the wgpu surface. The feature request to render a webview over native GPU content (tauri #8246, November 2023) is closed without a built-in solution. The suggested workaround is two stacked windows, a topmost transparent overlay with click-through toggling. — [wry examples/wgpu.rs](https://github.com/tauri-apps/wry/blob/dev/examples/wgpu.rs); [wry #1212](https://github.com/tauri-apps/wry/issues/1212); [wry #1331](https://github.com/tauri-apps/wry/issues/1331); [tauri discussion #11944](https://github.com/tauri-apps/tauri/discussions/11944); [tauri #8246](https://github.com/tauri-apps/tauri/issues/8246); [dceddia/wgpu-tauri-experiment](https://github.com/dceddia/wgpu-tauri-experiment)

### Inferences
- Throughput math: raw RGBA at 1280×720 is about 3.7 MB/frame, or about 221 MB/s at 60 FPS; 1080p60 is about 498 MB/s. Every frame has to be serialized across the IPC bridge, copied into a JS ArrayBuffer, then `putImageData` or `texImage2D`. JPEG-encoding each frame (about 100–200 KB) makes the transport cheap but adds encode and decode cost plus latency on both sides. Getting under a 16 ms frame budget reliably, especially on WebKitGTK, is unlikely. The published measurements (6.7 ms for 64 KB over JSON) show the default path is far too slow, and no source shows stable 1080p60 raw frames in Tauri.
- Best Tauri option if Tauri is mandatory: encode the swapped frames to H.264/VP8 with a hardware encoder, then either use WebCodecs `VideoDecoder` → canvas via a binary Channel, or use MSE fMP4 over a custom protocol. This adds encoder latency (tens of ms) and needs WebCodecs support in the webview. WebKitGTK/WKWebView WebCodecs coverage was not verified.
- Final verdict: build the preview natively (egui or Slint on wgpu, with the inference output uploaded or rendered straight into a wgpu texture). If a web UI is wanted for settings, use a separate Tauri window or embed a webview only for non-video panels. Do not route 30–60 FPS video through the webview.

### Gaps
- I found no published Tauri benchmark of 720p/1080p raw frames per second via `ipc::Channel` or a custom protocol on Windows, macOS and Linux. The only hard numbers are for payloads of 64 KB or less.
- I did not verify WebCodecs availability in WebKitGTK and WKWebView as of 2026, or practical shared-memory hacks (SharedArrayBuffer is not exposed from Rust).

## Virtual camera output on Linux, Windows 10/11 and macOS: Rust options, OS APIs, and reusing the OBS virtual camera

### Takeaway
There is no mature permissive-license cross-platform Rust virtual-camera crate.

- **Linux:** write to v4l2loopback, which works with every app, or register a PipeWire Video/Source node, which only PipeWire-aware consumers see.
- **Windows 11:** implement a Media Foundation media source as a COM DLL, register it once as admin, and activate it via `MFCreateVirtualCamera`.
- **Windows 10:** a DirectShow filter is required. The practical shortcut is writing NV12 into OBS's documented shared-memory queue `OBSVirtualCamVideo` when OBS is installed.
- **macOS 13+:** a CoreMediaIO Camera Extension, a signed and notarized Swift/ObjC system extension, is mandatory. Reusing OBS's camera from outside OBS is not a stable route.

### Cited Findings
- The **`virtualcam` crate** (Jagirium) v1.0.0 was released July 22, 2026, under the **AGPL-3.0** license. Backends: a bundled Media Foundation "VCam" transport on Windows 11, the OBS Virtual Camera as a Windows 10/11 fallback, and V4L2 via v4l2loopback on Linux. **No macOS support.** It accepts RGB, BGR, RGBA, gray, I420, NV12, YUYV and UYVY frames, and can publish GPU frames via optional `cudarc`. It sees about 27 downloads a month. — [lib.rs virtualcam](https://lib.rs/crates/virtualcam); [GitHub Jagirium/virtualcam](https://github.com/Jagirium/virtualcam); [crates.io](https://crates.io/crates/virtualcam)
- `rust-virtual-cam` registers a Windows 11 virtual camera with `MFCreateVirtualCamera` using only the `windows` crate. It captures the monitor via Windows.Graphics.Capture and converts to NV12 on the GPU. The API does not exist on Windows 10. — [sinnafuls/rust-virtual-cam](https://github.com/sinnafuls/rust-virtual-cam); `windows` crate binding: [MFCreateVirtualCamera in windows-rs](https://microsoft.github.io/windows-docs-rs/doc/windows/Win32/Media/MediaFoundation/fn.MFCreateVirtualCamera.html)
- `MFCreateVirtualCamera` requires Windows build 22000 or later (mfsensorgroup.dll). Only `MFVirtualCameraType_SoftwareCameraSource` is supported. `sourceId` is the "{CLSID}" of a custom COM media source. Lifetime `Session` removes the camera when the object is released; `System` persists across reboots. `AllUsers` access needs admin. " Windows Virtual Camera" is appended to the friendly name. The call is subject to the webcam privacy toggle (E_ACCESSDENIED), and packaged apps must declare the webcam capability and must not call it on the UI thread. — [Microsoft Learn MFCreateVirtualCamera](https://learn.microsoft.com/en-us/windows/win32/api/mfvirtualcamera/nf-mfvirtualcamera-mfcreatevirtualcamera); [IMFVirtualCamera](https://learn.microsoft.com/en-us/windows/win32/api/mfvirtualcamera/nn-mfvirtualcamera-imfvirtualcamera)
- The reference implementation is smourier/VCamSample: a media source DLL that outputs RGB32 and NV12, plus a driver app that calls `MFCreateVirtualCamera`. The DLL must be registered in **HKLM** with `regsvr32` as administrator because it is loaded by multiple processes, including the Frame Server. It uses the Video Processor MFT on the GPU when a D3D manager is present and CPU RGB→NV12 otherwise. There are also a .NET/AOT port and derivatives such as WinCamHTTP. — [smourier/VCamSample](https://github.com/smourier/VCamSample); [VCamNetSample](https://github.com/smourier/VCamNetSample); [kbralten/WinCamHTTP](https://github.com/kbralten/WinCamHTTP); [alax.info write-up](https://alax.info/blog/2245)
- **OBS Windows virtual camera shared-memory protocol:** a named file mapping `L"OBSVirtualCamVideo"`. Its header holds `volatile state`, `cx`, `cy`, a `uint64 interval`, `offsets[3]`, and `volatile write_idx` / `read_idx`. It is a 3-frame ring buffer in **NV12** (`cx*cy*3/2`) with states STARTING → READY → STOPPING. The reader treats the stream as stalled after 10 reads without a new index. — [obs-studio shared-memory-queue.c](https://raw.githubusercontent.com/obsproject/obs-studio/master/shared/obs-shared-memory-queue/shared-memory-queue.c)
- DirectShow-based Windows virtual cameras include OBS, Softcam (MIT), akvirtualcamera (DirectShow filter on Windows, CoreMediaIO plugin on Mac) and the older CatxFish obs-virtual-cam. One project vendors Softcam with its own CLSID and shared-memory names to avoid depending on OBS. — [webcamoid/akvirtualcamera](https://github.com/webcamoid/akvirtualcamera); [CatxFish/obs-virtual-cam](https://github.com/CatxFish/obs-virtual-cam); [webcam-bridge PR #11](https://github.com/16SULPHUR/webcam-bridge/pull/11)
- pyvirtualcam backends: `v4l2loopback` (Linux), `obs` (Windows and macOS), `unitycapture` (Windows, RGBA). It relies on existing virtual camera drivers. On macOS the OBS backend broke when OBS 30 moved to a Camera Extension for macOS 14 (issue #111). A fork adds a Rust v4l2loopback backend. — [letmaik/pyvirtualcam](https://github.com/letmaik/pyvirtualcam); [pyvirtualcam API docs](https://letmaik.github.io/pyvirtualcam/); [pyvirtualcam #111](https://github.com/letmaik/pyvirtualcam/issues/111); [LuxTronic/pyvirtualcam fork](https://github.com/LuxTronic/pyvirtualcam)
- There is a v4l2loopback pitfall with `exclusive_caps=1`: "No v4l2 loopback device found" after using the device once. — [pyvirtualcam #61](https://github.com/letmaik/pyvirtualcam/issues/61)
- Linux Rust crates:
  - `v4l2loopback` crate: safe bindings to create and manage devices. It targets an unreleased v4l2loopback version, so you must build the module from source, and it needs root to open `/dev/v4l2loopback`.
  - `v4l` crate: focused on capture. Writing to an output device is possible at the ioctl level, but the examples are capture-only.
  — [docs.rs v4l2loopback](https://docs.rs/v4l2loopback); [crates.io v4l2loopback](https://crates.io/crates/v4l2loopback); [docs.rs v4l](https://docs.rs/v4l)
- PipeWire: `pipewire-vircam` (Rust) registers a Video/Source node in the PipeWire/WirePlumber graph that any PipeWire-aware consumer can select. It is framed as the more idiomatic alternative to v4l2loopback, whose devices have a fixed resolution. A Rust re-implementation of the PipeWire protocol is underway (Collabora, PipeWire workshop 2025). GStreamer's `pipewiresink` can also create a virtual camera. — [simon3z/pipewire-vircam](https://github.com/simon3z/pipewire-vircam); [Ideas on Board: "PipeWire is the new v4l2loopback"](https://www.ideasonboard.com/news/pipewire-is-the-new-v4l2loopback/); [Collabora PipeWire workshop 2025](https://www.collabora.com/news-and-blog/blog/2025/07/03/pipewire-workshop-2025-updates-video-transport-rust-bluetooth/)
- macOS: since macOS 13, Camera Extensions (CMIO extensions) replace deprecated DAL plug-ins. They are loaded by the OS rather than injected into the host process, and must ship inside a codesigned and notarized app bundle with the System Extension capability. OBS added its macOS 13+ camera extension in PR #7777 (OBS 30). The system extension can be hard to uninstall if the app is deleted outside Finder (OBS #9714). — [Apple WWDC22 "Create camera extensions with Core Media IO"](https://developer.apple.com/videos/play/wwdc2022/10022/); [OBS PR #7777](https://github.com/obsproject/obs-studio/pull/7777); [OBS #9714](https://github.com/obsproject/obs-studio/issues/9714); [Halle Winkler CMIO extension guide](https://theoffcuts.org/posts/core-media-io-camera-extensions-part-one/); [Apple forum: invalid signature on install](https://developer.apple.com/forums/thread/710046)

### Inferences
- **Can our app just write to OBS's virtual camera shared memory?**
  - **Windows:** yes, technically. Open or create the `OBSVirtualCamVideo` mapping and write NV12 frames into the 3-slot ring with the documented header. This is what pyvirtualcam's `obs` backend and the `virtualcam` crate's fallback do. It requires OBS to be installed so its DirectShow filter DLL is registered, and it is an undocumented internal protocol that could change. It also conflicts if OBS itself starts its virtual camera.
  - **macOS:** effectively no. OBS's Camera Extension talks to OBS over a private channel, and pyvirtualcam's OBS backend broke on macOS 14.
  - **Linux:** unnecessary. Write directly to v4l2loopback.
- **Recommended plan:**
  - **Linux:** write YUYV/NV12 frames with `write()` or V4L2 output ioctls to a v4l2loopback device, created with `modprobe v4l2loopback devices=1 exclusive_caps=1 card_label="FaceSwap Cam"`. Optionally add a PipeWire node for Flatpak or portal-based apps. PipeWire-only cameras are not visible to V4L2-only apps, and many conferencing apps are V4L2-only, so v4l2loopback stays primary.
  - **Windows 11:** write a small MF media source DLL in Rust using the `windows` crate's `implement` macro, or reuse VCamSample in C++. It reads frames from your own shared-memory ring, and `MFCreateVirtualCamera` activates it. You need a one-time admin registration in the installer.
  - **Windows 10:** a DirectShow filter such as Softcam (MIT) with your own CLSID, or the OBS-shared-memory fallback.
  - **macOS:** a Swift CMIO Camera Extension target inside the signed and notarized .app, fed through IOSurface or an XPC sink stream from the Rust process. This is unavoidable native Swift work, and an Apple Developer ID is required.
- **Licensing warning:** the only cross-platform Rust crate (`virtualcam`) is AGPL-3.0, which is viral for distributed apps. Use it as a reference or accept AGPL. It also lacks macOS.

## How Deep-Live-Cam, FaceFusion and DeepFaceLive handle virtual camera output today

### Takeaway
None of the three ships its own cross-platform virtual camera driver.

- **Deep-Live-Cam:** users capture the preview window with OBS and use OBS Virtual Camera. A `--virtual-cam` flag via pyvirtualcam was proposed in 2026 but the issue is closed without a merge.
- **FaceFusion:** offers inline preview, a UDP stream (`udp://localhost:27000`) for OBS, and a v4l2 output on Linux.
- **DeepFaceLive:** recommends OBS Window Capture or an mpegts UDP stream into OBS.

### Cited Findings
- Deep-Live-Cam issue #1662 (February 22, 2026) proposed a `--virtual-cam` flag using optional `pyvirtualcam`: OBS Virtual Camera on macOS/Windows and v4l2loopback on Linux, with about 0.1 ms per frame send time. The contributor has a fork implementation. The issue is closed and nothing is merged upstream. Users currently need OBS in the middle for Zoom, Meet or Discord. — [Deep-Live-Cam #1662](https://github.com/hacksider/Deep-Live-Cam/issues/1662); earlier user code in [Deep-Live-Cam discussion #76](https://github.com/hacksider/Deep-Live-Cam/discussions/76); OBS workflow guide [heyletslearnsomething](https://heyletslearnsomething.com/blog/use-obs-virtual-camera-and-deeplivecam-with-whatsapp-desktop)
- A third-party Windows fork of Deep-Live-Cam advertises CUDA/DirectML and "OBS virtual-camera output". — [CRSD-Lau/deep-live-cam](https://github.com/CRSD-Lau/deep-live-cam)
- FaceFusion webcam modes: **Inline** (render in the UI), **UDP** (stream to `udp://localhost:27000` for OBS) and **V4L2** (a `/dev/video*` virtual device). — [FaceFusion docs: Deepfake Webcam](https://docs.facefusion.io/usage/deepfake-webcam)
- DeepFaceLive (Windows) for streaming: in OBS, add a Window Capture of the DeepFaceLive output window, add the microphone as Audio Input Capture, and set the audio Sync Offset to DeepFaceLive's "Target Delay". Alternatively, add an OBS Media Source reading DeepFaceLive's mpegts UDP output. Third-party scripts route its output into a virtual camera with pyvirtualcam and OpenCV. — [DeepFaceLive for_streaming.md](https://github.com/iperov/DeepFaceLive/blob/master/doc/windows/for_streaming.md); [m-a-r-i-b/deepfacelive-virtualcam](https://github.com/m-a-r-i-b/deepfacelive-virtualcam)

### Inferences
- A Rust app with its own native virtual camera would be a real differentiator over all three incumbents, which rely on OBS as middleware on Windows and macOS. At minimum, match FaceFusion's pattern: v4l2loopback on Linux, plus an OBS shared-memory writer on Windows and a UDP/mpegts output as a universal fallback.
- Audio/video sync, meaning delaying the mic by the pipeline latency, is an issue the incumbents leave to OBS. A native virtual camera leaves A/V sync to the conferencing app, so keep end-to-end latency low.
